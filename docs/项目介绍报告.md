## 摘要

本项目是一个面向小型餐厅的点餐与经营管理演示系统，采用“微信小程序 + Spring Boot + MySQL”的前后端分离架构。顾客端支持按分类浏览菜品、搜索、加入购物车、选择桌号、提交订单和查看历史订单；老板端支持密码登录、订单看板、接单/出餐/取消、菜品新增与编辑、上下架、库存调整和经营统计。

系统重点解决了三个课程设计中的核心问题：一是订单主表、订单明细、库存与销量之间的事务一致性；二是订单状态流转的合法性；三是历史订单金额不因菜品后续改价而失真。项目还提供了统一的响应结构、全局异常处理、老板端接口鉴权、数据库索引与视图，以及便于现场演示的数据初始化和降级策略。

**关键词**：餐厅点餐；微信小程序；Spring Boot；MyBatis；MySQL；事务；订单状态机

## 一、项目概述

### 1.1 项目背景

传统小型餐厅常见的问题是：点餐依赖人工记录，高峰期容易漏单、错单；订单状态不透明，顾客不知道菜品是否已接单、是否出餐；老板也难以快速查看当日营业额、热销菜品和待处理订单。

本项目用一套轻量的前后端系统模拟“顾客扫码点餐 + 老板后台管理”的完整流程，重点不是做商业级收银系统，而是通过一个可运行、可演示、可讲解的课程项目，体现数据库设计、事务控制、接口设计和前后端协作。

### 1.2 项目目标

1. 顾客能在小程序内完成“选菜 → 购物车 → 选桌号 → 下单 → 查看订单”的闭环。
2. 老板能登录后台，查看订单、推进状态、管理菜品、查看经营统计。
3. 下单和取消订单时，订单、明细、库存、销量保持一致。
4. 订单状态只能按业务规则流转，不能随意跳过或回退。
5. 代码结构清晰，数据库设计规范，能够在答辩现场稳定演示。

### 1.3 项目规模

- 小程序页面：7 个
- Java 后端源文件：约 30 个
- 数据库表：5 张
- 数据库视图：1 个
- REST 接口：20 个左右
- 主要角色：顾客、老板

### 2.1 顾客端需求

| 编号 | 需求 | 说明 |
|---|---|---|
| C1 | 浏览菜品 | 按分类查看在售菜品，展示图片、名称、价格、销量、库存 |
| C2 | 搜索菜品 | 按名称模糊搜索 |
| C3 | 购物车 | 加菜、减菜、清空、计算总价 |
| C4 | 选择桌号 | 从空闲/可用餐桌中选择 |
| C5 | 提交订单 | 校验桌号、菜品状态、库存，生成订单号 |
| C6 | 查看订单 | 查看历史订单及明细 |
| C7 | 取消订单 | 仅允许待处理/制作中的订单取消 |

### 2.2 老板端需求

| 编号 | 需求 | 说明 |
|---|---|---|
| O1 | 老板登录 | 密码校验，返回 8 小时有效的令牌 |
| O2 | 订单看板 | 按状态筛选订单，查看桌号、菜品、金额、时间 |
| O3 | 订单流转 | 接单、出餐、完成、取消 |
| O4 | 菜品管理 | 新增、编辑、改价、改库存、上下架 |
| O5 | 经营统计 | 今日订单/营业额、待处理订单、累计营业额、热销榜、分类占比 |
| O6 | 鉴权保护 | 除登录外，老板接口必须携带 `X-Owner-Token` |

### 2.3 非功能需求

- **一致性**：下单、取消订单必须使用事务，避免“订单生成了但库存没扣”或“库存退了但订单没取消”。
- **安全性**：老板接口统一鉴权；价格以服务端数据库为准，不信任前端传入金额。
- **可演示性**：提供健康检查、初始数据、本地菜品图和前端降级策略，避免现场网络或接口异常导致演示中断。
- **可维护性**：Controller / Service / Mapper / Entity / DTO 分层，SQL 与 Java 分离。

## 四、系统架构

### 4.1 总体架构

```text
微信小程序
   │  wx.request（HTTP + JSON）
   ▼
Spring Boot 后端
   ├── Controller  接收请求、参数校验、返回统一 Result
   ├── Service     业务规则、事务、状态机
   ├── Mapper      MyBatis 接口
   └── XML SQL     动态 SQL、库存扣减、统计查询
   │
   ▼
MySQL（category / dish / dining_table / orders / order_item / v_order_detail）
```

### 4.2 后端分层

| 层 | 职责 | 代表类 |
|---|---|---|
| Controller | 暴露 REST 接口，接收参数，调用 Service | `MenuController`、`OrderController`、`OwnerController` |
| Service | 业务规则、事务边界、状态校验 | `OrderService`、`MenuService`、`OwnerAuthService`、`StatsService` |
| Mapper | 数据库访问接口 | `MenuMapper`、`OrderMapper`、`StatsMapper`、`TableMapper` |
| Entity | 与表结构对应的实体 | `Dish`、`Order`、`OrderItem`、`DiningTable`、`Category` |
| DTO | 接收前端参数 | `OrderCreateDTO`、`DishSaveDTO`、`OwnerLoginDTO` |
| Common | 统一响应、异常、业务异常 | `Result`、`BizException`、`GlobalExceptionHandler` |
| Config | 跨域、老板端鉴权 | `CorsConfig`、`OwnerAuthInterceptor`、`OwnerWebConfig` |

### 4.3 统一响应

所有接口返回：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

- `code = 0`：成功
- `code != 0`：业务失败或系统异常
- 前端 `utils/api.js` 统一判断 `code`，失败时抛出带 `message` 的错误

### 4.4 老板端鉴权

```text
POST /api/owner/login
  → 校验密码
  → 生成随机 token
  → 存入内存 Map<token, 过期时间>
  → 返回 token

后续 /api/owner/**
  → OwnerAuthInterceptor 读取 X-Owner-Token
  → 校验存在且未过期
  → 通过则放行，否则返回 401
```

课程演示采用内存会话，重启后 token 失效；生产环境应改为持久化会话、JWT 或统一认证中心。

## 五、数据库设计

### 5.1 数据表

| 表名 | 中文名 | 主要字段 | 说明 |
|---|---|---|---|
| `category` | 菜品分类 | id、name、sort_order | 热菜 / 凉菜 / 主食 / 饮品 |
| `dish` | 菜品 | category_id、name、price、sales、stock、status | 价格用 `DECIMAL(10,2)`，库存和销量用于下单 |
| `dining_table` | 餐桌 | table_no、seats、status | 桌号唯一；0 空闲、1 使用中 |
| `orders` | 订单主表 | order_no、table_no、total_amount、status | 订单号唯一；状态为中文枚举 |
| `order_item` | 订单明细 | order_id、dish_id、dish_name、price、count、subtotal | 保存菜品名称与单价快照 |
| `v_order_detail` | 订单详情视图 | 主表 JOIN 明细 | 便于报表查询 |

### 5.2 E-R 关系

```text
CATEGORY 1 ── N DISH
DISH     1 ── N ORDER_ITEM
ORDERS   1 ── N ORDER_ITEM
DINING_TABLE 1 ── N ORDERS（按 table_no 逻辑关联）
```

- `dish.category_id → category.id`：外键
- `order_item.order_id → orders.id`：外键，级联删除
- `order_item.dish_id`：逻辑关联，不建外键，避免菜品下架/删除影响历史订单
- `orders.table_no`：逻辑关联，按桌号匹配

### 5.3 设计要点

1. **金额精度**：`DECIMAL(10,2)` + Java `BigDecimal`，避免 `double` 浮点误差。
2. **订单快照**：`order_item` 保存下单时的 `dish_name`、`price`、`emoji`，菜品后续改名改价不影响历史订单。
3. **索引**：分类、状态、下单时间、桌号、订单明细外键均有索引，支撑筛选和统计。
4. **视图**：`v_order_detail` 把订单主表与明细关联，便于报表类查询。
5. **状态字段**：`orders.status` 使用中文枚举，和前端展示一致；Service 中通过状态机限制流转。

## 六、功能实现

### 6.1 顾客点餐流程

```text
进入点餐页
  → 加载分类和菜品
  → 选择分类/搜索
  → 加入购物车
  → 进入确认页
  → 选择桌号、填写备注
  → 提交订单
  → 后端校验桌号、菜品、库存
  → 写订单主表 + 明细 + 扣库存/加销量
  → 返回订单详情
  → 订单页查看
```

关键点：

- 价格以数据库为准，不信任前端金额。
- 菜品必须是在售状态。
- 库存不足时返回明确错误。
- 订单号格式：`D + yyyyMMddHHmmss + 3 位随机数`。

### 6.2 老板订单看板

```text
老板登录
  → 进入订单看板
  → 按状态筛选
  → 接单：待处理 → 制作中
  → 出餐：制作中 → 已完成
  → 取消：待处理/制作中 → 已取消
  → 取消时回滚库存与销量
  → 完成/取消后刷新餐桌状态
```

状态机：

```text
待处理 ──接单──▶ 制作中 ──出餐──▶ 已完成
   │                 │
   └────取消─────────┴────▶ 已取消
```

不允许：

- 已完成 → 制作中
- 已取消 → 待处理
- 跳过制作中直接完成

### 6.3 菜品管理

- 新增菜品：校验分类、名称、价格、库存
- 编辑菜品：不允许直接改销量；销量由下单/取消维护
- 上下架：停售采用软下架，顾客菜单不再显示，但历史订单仍保留快照
- 库存：老板可调整；下单扣减、取消回退

### 6.4 经营统计

- 今日订单数、今日营业额
- 累计订单数、累计营业额、客单价
- 待处理订单数
- 餐桌占用情况
- 热销菜品 Top 5
- 分类营业额占比

统计由 `StatsMapper` 的聚合 SQL 完成，Service 只做客单价等少量计算。

## 八、关键设计说明

### 8.1 事务一致性

`OrderService.createOrder` 使用 `@Transactional(rollbackFor = Exception.class)`：

1. 校验桌号
2. 逐条校验菜品、计算金额
3. 写订单主表
4. 写订单明细 + 扣库存/加销量
5. 更新餐桌状态

任意一步失败，整个事务回滚。

取消订单同样使用事务：

1. 校验状态流转
2. 更新订单状态
3. 回滚每个菜品的库存与销量
4. 重算餐桌状态

### 8.2 订单状态机

状态机集中在 `OrderService.TRANSITIONS`：

```java
待处理 → 制作中 / 已取消
制作中 → 已完成 / 已取消
已完成 → 无
已取消 → 无
```

这样 Controller 不需要散落状态判断，业务规则集中、可测试、可讲解。

### 8.3 价格与快照

- 下单金额完全由数据库菜品单价计算。
- 明细保存 `dish_name`、`price`、`emoji` 快照。
- 后续老板改价、改名、停售，不会改变历史订单。

### 8.4 统一异常处理

`GlobalExceptionHandler` 把：

- `BizException`：业务错误，返回业务 code 和友好提示
- 参数校验异常：返回第一条字段错误
- 其他异常：返回 500 和日志

前端只需要判断 `code` 和展示 `message`。

### 8.5 前端降级

小程序接口不可用时，部分页面会切换到本地菜品数据，保证课堂演示不中断；这是演示策略，不是生产级离线方案。

## 十、项目亮点

1. **完整业务闭环**：顾客点餐 + 老板管理 + 统计报表，不是单表 CRUD。
2. **事务一致性**：下单、取消订单都有明确事务边界。
3. **订单状态机**：状态流转集中管理，避免非法跳转。
4. **历史订单快照**：菜品改价不影响历史金额。
5. **金额精度**：`BigDecimal` + `DECIMAL(10,2)`。
6. **数据库设计规范**：主外键、索引、视图、软下架。
7. **老板端鉴权**：密码 + 内存令牌 + 拦截器，接口边界清晰。
8. **统一响应与异常**：前后端契约稳定，错误提示友好。
9. **可演示性**：健康检查、初始数据、本地图片、前端降级。
10. **双后端方案**：Java 主方案 + Node 备用方案，降低环境风险。

## 十一、不足与改进

### 11.1 当前不足

1. **自动化测试不足**：`src/test` 目前为空，主要依赖手工接口验证和构建检查。
2. **老板端会话在内存**：重启后 token 失效，多实例部署不共享。
3. **密码为演示配置**：默认 8888，未做哈希存储；只适合课程演示。
4. **库存并发**：当前先查库存再扣减，单机演示足够，但高并发下可能出现超卖。
5. **无分页**：订单列表用 `limit` 截断，数据量大时体验一般。
6. **无幂等**：重复提交同一订单可能生成多笔订单。
7. **无操作日志**：老板改价、上下架、取消订单没有审计记录。

### 11.2 可落地的小改进

- 库存扣减 SQL 增加 `AND stock >= #{count}`，并检查受影响行数。
- 500 响应改为通用提示，详细异常只写日志。
- 增加 `docs/演示脚本.md` 和一键重置演示数据 SQL。
- 给 P0 文件补充“为什么”注释，不逐行注释。
- 老板端增加退出接口，服务端删除 token。
- 订单提交增加幂等键或前端防重复点击。
- 后续可补 2–3 个接口级集成测试。

## 十二、答辩提纲

### 12.1 三分钟介绍顺序

1. **一句话**：这是一个顾客点餐 + 老板管理的餐厅系统。
2. **架构**：小程序 → Spring Boot → MyBatis → MySQL。
3. **数据库**：5 表 + 1 视图，重点讲订单/明细/菜品/餐桌关系。
4. **核心流程**：下单事务、库存扣减、老板状态机、取消回滚。
5. **亮点**：金额精度、订单快照、统一异常、老板鉴权。
6. **不足**：测试、并发、会话持久化，说明后续改进。
7. **演示**：按“点餐 → 老板接单 → 统计 → 取消回滚”走一遍。

### 12.2 老师可能追问

| 问题 | 回答要点 |
|---|---|
| 为什么订单明细要存菜品名称和价格？ | 这是下单瞬间的快照，防止菜品后续改价导致历史订单金额变化 |
| 为什么用 `BigDecimal`？ | 金额不能用 double，`BigDecimal` + `DECIMAL(10,2)` 保证精度 |
| 下单失败会怎样？ | `@Transactional` 回滚订单主表、明细、库存、销量 |
| 取消订单库存怎么回退？ | 根据订单明细逐条回加库存、回减销量，并重算餐桌状态 |
| 老板端怎么鉴权？ | 登录发 token，拦截器校验 `X-Owner-Token`，过期返回 401 |
| 订单状态能随便改吗？ | 不能，`TRANSITIONS` 状态机限制正向流转和取消 |
| 项目有什么不足？ | 自动化测试、并发扣库存、内存会话、密码哈希、分页和幂等 |

## 十三、总结

本项目完成了一个可运行的餐厅点餐与经营管理闭环，覆盖了课程设计中的主要知识点：前后端分离、REST 接口、MyBatis 动态 SQL、数据库表关系与索引、事务一致性、订单状态机、统一异常处理和接口鉴权。

它的价值不只在“功能能跑”，更在于把几个关键业务问题讲清楚：订单和库存如何保持一致、历史订单如何不被改价影响、老板端接口如何保护、订单状态如何合法流转。后续如果继续完善，优先补自动化测试、库存并发防护和演示脚本，而不是继续堆功能。
